# Template — migration report

Every migration (in place or rewrite) delivers **two files** committed to the target repo:

1. **`migration/report.html` — the report, as an executive dashboard.** **Must be generated by
   `scripts/report-dashboard.py`** from a versioned `migration/report.json` (data) + the cobertura
   (measured coverage) — hand-writing the HTML is forbidden (skill rule 7: determinism).
   **Self-contained** HTML document (full doctype, inline CSS/JS, screenshots embedded as data URIs
   — double-clickable, emailable to a decision-maker). Light/dark theme, validated palette (see the
   audit dashboard's dataviz method). Sections in order: result banner + Verified badge · KPI tiles
   (tests, **measured coverage** — coverlet/cobertura, never estimated —, errors/warnings, business
   figure, estimated vs actual) · **business value** (what the migration changes: reactivated
   asset, risk retired with proof, maintenance cost, reusability) · product screenshot · coverage
   by class (chart) · before/after · code ported vs written vs tested · gates cleared (one per
   commit) · **pipeline timeline** (`phases[]` — minutes per phase, derived from gate commits,
   never hand-timed; see phase-6-verify §7) · **Next steps** · Deferred follow-ups · **wave
   lessons** (`lessons` — fed back into the kit, or an explicit "nothing to learn"; see
   delivery-playbook §9) · method and limitations.
2. **`migration/report.md` — the diffable summary** (grep/diff-friendly): the same figures
   condensed, with a link to the dashboard.

⚠ **`coverage.cobertura` must name a DIRECTORY, not a file.** Under Microsoft Testing Platform,
each test project writes its own report and the collector names it, with a fresh identifier on
every run:

```json
"coverage": { "cobertura": "../coverage", "exclude": ["MonApp.Web"] }
```

⚠ **A relative path resolves against the `report.json`'s directory, not the repo root.** The
report lives in `migration/` and `templates/ci-dotnet.yml` writes its reports into the **root**'s
`coverage/`: the correct path therefore climbs one level up, `"../coverage"`. Writing `"coverage"`
would name `migration/coverage`, where nothing ever writes.

This resolution makes `migration/` self-contained for everything it holds — but `../coverage`
reaches precisely outside the folder, so **moving `migration/` elsewhere breaks report
regeneration**. That is the accepted price of reading coverage where CI writes it; the produced
HTML, for its part, stays self-contained (inline CSS/JS, screenshots as data URIs) and moves
without breaking anything.

The field also accepts a file, a list of files, or a glob pattern, but a literal path written into
a versioned `report.json` will be stale by the next run. And picking **one** among several would
republish a single project's coverage as the app's — exactly the flaw per-project collection
corrects. `report-dashboard.py` aggregates whatever reports it finds (union of lines, never a sum
of percentages).

⚠ **The coverage KPI tile is CALCULATED, never copied in.** `report-dashboard.py` replaces the
value written in `kpis` with the measurement — the same one shown as `Overall: N%` under the
chart. Hand-writing a number into this tile therefore has no effect: the page can no longer
publish two contradictory coverage figures.

The tile can declare what it renders, and that is the preferred form:

```json
{ "v": "0", "unit": "%", "label": "measured coverage (lines)", "source": "line_pct" }
```

`source` is either `line_pct` or `branch_pct`. Without it — the case for every `report.json`
written before — the tile is recognized by its label: a `%` unit and a label naming *coverage*,
which renders lines, or branches if the label speaks of branches. A tile that is not a coverage
figure (`green tests`, a business figure) is never touched. **Declare `source` explicitly** rather
than relying on this fallback: `report-dashboard.py` still matches the label against the French
substring `couvertur` (#432 tracks translating the generator itself), so an English-only label with
no `source` field is not recognized yet.

⚠ **An unmeasured quantity displays `n/a`, never `0%`.** A zero is a number, and on this page a
number reads as a measurement. Two cases:

- **Branches.** The rate comes from per-line `condition-coverage` when every report carries it;
  failing that, from the root `branch-rate`, but only for a **single, unfiltered** report — it is
  a global rate, it ignores `exclude`/`include`, and averaging it across several reports would
  make no sense. Outside of that: `branches n/a`.
- **Lines.** If `exclude`/`include` filter until nothing is left — an `include` naming a class that
  no longer exists after a rename, typically — the caption reads `lines n/a` instead of `0%`. The
  tile then keeps the written value, for lack of a measurement: that is the sign the filter needs
  fixing.

⚠ The `coverage` field remains **mandatory**: the report is generated from a cobertura, and a
`report.json` without it does not generate at all. A hand-written tile is not an escape hatch for
publishing unmeasured coverage.

"Next steps" are an **actionable checklist** with an estimated effort — that is the hand-off: the
person who picks up the repo knows what to do without reading the history. Structure of the
markdown summary:

```markdown
# Migration report — <app> (<source> → <target>)

**Date:** <yyyy-mm-dd> · **Pipeline:** ai-migration-kit <command> · **Branch:** migration/<date>

## Before / after
| | Before | After |
(platform/TFM, packages, diagnostics, tests, notable points — measured figures only)

## Tests
**Test platform:** <VSTest | Microsoft Testing Platform> · **Tests run:** <n> (baseline <n>)
(the phase 5 "xunit v2 → v3" item: applied, not requested, or `deferred: <named blocker>`)

## Gates cleared
(one entry per green gate = per commit: what was done, with proof)

## Verification
(build, tests, diagnostics vs baseline, runtime smoke test — actual results)

## Estimated vs actual
(the audit figure, the actual, the gap explained)

## Dependency health
**Status:** <ok | findings> · **Checked on:** <ISO 8601> (the `dependencyHealth` block of
`migration/report.json`, produced by `scripts/dependency-health.sh` — phase-6-verify §4)

| Package | Version | Type | Severity | Advisory |
|---|---|---|---|---|
| <id> | <resolved> | vulnerable / deprecated, and **top-level or transitive** (`transitive` field) | <low\|moderate\|high\|critical> or n/a | <advisory URL> or <alternative package> |

("none" when both lists are empty — the section stays, because the reader must be able to tell
*measured, nothing found* from *never measured*.)

⚠ This section is mandatory in **`report.md`**, and only there for now: `report-dashboard.py`
does not yet know about `dependencyHealth`, and hand-writing the HTML is forbidden (rule 7).
Adding it to the `report.html` section list above would make mandatory a card the generator does
not produce — a requirement nothing can satisfy. The dashboard card is an explicit non-goal of
#267 ("worth doing; not this issue"); the `report.html` section list only moves alongside it.

Every row above has its counterpart in **Next steps** (owner decision: upgrade, accept the risk,
replace with the named alternative) or in **Deferred follow-ups** with the report's WHY. A finding
that appears only in this table has no owner.

This table is a **snapshot at delivery date**, not monitoring: the ongoing complement is
Renovate/Dependabot enabled on the delivered repo (phase 7, CI) — that is what will catch next
week's published CVE.

## Next steps
- [ ] <concrete, ordered action, with estimated effort> (e.g.: merge the branch, deploy with SPA
      fallback, wire CI to the tests, decisions pending with the owner)

## Deferred follow-ups
(documented, uncorrected quirks; modernizations left out; v2 ideas — with the report's WHY)
```

Rules:
- **Next steps ≠ follow-ups.** The former is the critical path to production (to do, ordered);
  the latter are opportunities (optional, dated, justified).
- Every figure the report states must be reproducible (a command or test that verifies it).
- The report lives in `migration/`, never in the product's UI (skill rule 6).

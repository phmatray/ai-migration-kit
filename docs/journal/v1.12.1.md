# v1.12.1: the lifecycle skills stop believing the wrong oracle

*Released 2026-08-19.* The patch that landed the day after the issue lifecycle got its outlet, and
found that most of what the lifecycle skills were reading as truth was not truth.

## What we were trying to fix

A patch release is a story about what the minor before it got wrong, and this one is unusually
tidy on that score. `v1.12.0` had just handed the kit a full issue lifecycle: file, plan, implement,
merge, triage. Running that lifecycle in anger for one day turned up a family of bugs that all had
the same shape.

`merge-pr` was deciding whether a merge had happened by reading `gh`'s exit code
([#178](https://github.com/phmatray/ai-migration-kit/issues/178)). A non-zero exit from the CLI
tells you the command was unhappy; it does not tell you what GitHub did, and the two disagree often
enough to matter. The same skill was judging CI by looking at every workflow run recorded against a
SHA ([#91](https://github.com/phmatray/ai-migration-kit/issues/91)), so a job that failed once and
then passed on a re-run kept the PR red forever, because the failed run never goes away.

`tick-plan.sh` could hang. Its `gh` calls had no bound, so a slow or stuck PATCH held the whole
worker ([#135](https://github.com/phmatray/ai-migration-kit/issues/135)). And the report renderer
raised a bare `KeyError` when it met a screenshot format it did not support
([#142](https://github.com/phmatray/ai-migration-kit/issues/142)), which is the least useful thing
an error can do: it names a dictionary lookup instead of the file the user gave it.

## What we decided

In every case, ask the authority rather than a proxy for it.

`merge-pr` now reads GitHub's own merge state
([#181](https://github.com/phmatray/ai-migration-kit/pull/181)), and judges CI by the latest run per
job rather than by the union of all runs on the SHA
([#190](https://github.com/phmatray/ai-migration-kit/pull/190)). That second one is the fix that
made re-running a flaky check actually mean something.

`tick-plan.sh` bounds every `gh` call, and the bound releases the caller
([#179](https://github.com/phmatray/ai-migration-kit/pull/179)). The second half of that sentence is
the part that took thought. Killing a call does not un-send it, so a timeout is not a failure and
must not be reported as one: the script reads the issue back and lets the read-back decide, which is
why the skill's instructions now say to re-run a bounded tick unchanged rather than restore the
original body over it.

The rest went the same way. Phase 6 collects coverage where the local flow's report actually reads
it ([#103](https://github.com/phmatray/ai-migration-kit/issues/103)), the report names an
unsupported screenshot format instead of raising
([#142](https://github.com/phmatray/ai-migration-kit/issues/142)), and the followups suite takes its
scratch directory from the shared test library like every other suite
([#160](https://github.com/phmatray/ai-migration-kit/issues/160)).

One performance change rode along: the audit reads every `.cs` file once instead of four or five
times ([#169](https://github.com/phmatray/ai-migration-kit/issues/169)). It is in a patch release
because it changed no behaviour, only how many times the disk was asked the same question.

## What got cut

Nothing was designed and dropped here, because nothing was designed here. A patch release has no
scope to trim: every change was already the smallest form of itself, and the two that were tempting
to widen (the CI judgement, and the merge state read) were kept to the single question each one was
answering rather than turned into a general GitHub state layer.

## What bit us

The recurring lesson of the release is that a zero exit is a claim about what a command attempted,
not about what happened. That is now doctrine in the guards, but this release is where it kept
costing real merges.

The `tick-plan` timeout is worth remembering on its own, because the wrong fix was obvious and
wrong. The instinct on a bounded call that expires is to treat the expiry as a failure and roll back.
Rolling back a plan tick that may still have arrived would silently un-tick completed work, so the
bound had to be paired with a read-back before it was safe to ship at all.
